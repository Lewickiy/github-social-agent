# UI.md — Перспективы развития UI дашборда GitHub Social Agent

> Аналитический документ. Цель — определить, какие блоки и возможности стоит добавить в веб-интерфейс, чтобы owner мог **эффективно и оперативно развивать свои социально-профессиональные связи в GitHub**.
>
> Документ основан на анализе фактической схемы данных (`core/database.py`, миграции), логики сбора (`services/collector.py`, `services/scorer.py`, `workers/snapshot_worker.py`, `workers/ml_trainer.py`) и текущего UI (`frontend/src`). Предложения сгруппированы по трём уровням приоритета. Каждое предложение содержит: решаемую проблему, вариант реализации, значимость и оценку сложности (1–5).

---

## 1. Текущее состояние: что собирается и что показывается

### Что система уже собирает (есть в БД)

| Сущность | Ключевые поля | Откуда |
|---|---|---|
| `users` | username, score, public_repos, followers, bio, company, status (NEW/FOLLOWED/FOLLOWBACK/UNFOLLOWED…/DELETED), discovered_from, scored_at, followed_at, score_version, repos_fetched_at, followers_count, followers_scanned_at, ml_follow_prediction, github_profile_json, owner | коллектор, скоринг, ML |
| `github_profile_json` | полный ответ API GitHub: name, location, blog, twitter_username, email, hireable, type, following, public_gists, created_at (возраст аккаунта) | каждый вызов `/users/{login}` |
| `repositories` | name, description, html_url, stars, forks, watchers, is_fork, is_archived, default_branch, created_at, repository_updated_at, last_checked_at | коллектор |
| `repository_languages` | язык ↔ репозиторий, **вес (%)** | коллектор |
| `topics` / `repository_topics` | топики репозиториев | коллектор |
| `companies` / `user_companies` | org-логины из поля company + обогащённые данные: name, description, location, email, twitter, followers, public_repos, company_type, avatar | `workers/company_worker` |
| `actions` | лог FOLLOW / UNFOLLOW по времени | follow-движок |
| `job_runs` | mode, status, pid, started_at, finished_at, exit_code, error | API / воркеры |
| `user_snapshots` | **ежедневные срезы** followers/following/public_repos/public_gists + extra_json (name, company, bio, location…) для любого пользователя | `workers/snapshot_worker` (сейчас — только owner, схема готова для всех) |
| ML-модель | метаданные: version, val_accuracy, num_samples, feature_order, top_languages, top_topics | `ml_service/trainer` (в логах) |

### Что UI показывает сейчас

- **Overview** — 8 KPI-карточек, график Followers growth (срезы owner), Pipeline status, Score distribution, Recent activity, Latest jobs.
- **Users** — таблица с поиском, фильтрами (status, language, ML), сортировкой, пагинацией; профиль в Drawer (языки, топики, компании, топ-репо, мета).
- **Management** — запуск джобов, конфигурация, история джобов с логами.

### Ключевые разрывы «собираем, но не показываем»

1. **Состав скоринга** — алгоритм считает base (0–35) и similarity (0–65, из них язык 30, топики 20, recency 15), но в БД хранится **только итоговый балл** → пользователь не понимает, *почему* тот или иной разработчик получил оценку.
2. **ML-модель** — точность, версия, число обучающих примеров есть в логах тренера, но не в UI.
3. **Компании/организации** — богатая таблица `companies` никак не агрегируется (нет «страницы компаний»).
4. **Срезы всех пользователей** — инфраструктура готова, но снапшотятся только данные owner; мини-история роста отдельной персоны недоступна.
5. **Глобальное распределение языков/топиков** — данные есть, дашборд их не агрегирует.
6. **Воронка follow → followback** — status + actions позволяют считать конверсию по времени, но графика нет.
7. **Профильные поля из `github_profile_json`** (возраст аккаунта, hireable, location, email, gists) частично скрыты.

## 2. Уровень 1 — быстрые победы (низкая сложность, данные уже есть)

### 2.1. Разбивка скоринга на компоненты (score breakdown)

- **Какую проблему решает.** Итоговый балл 0–100 непрозрачен: нельзя понять, что именно повлияло — совпадение языков, топиков, свежесть репозиториев или базовые метрики. Owner не может принимать решения «кого подписать» с обоснованием.
- **Как лучше реализовать.** Добавить в `Scorer.calculate()` (`services/scorer.py`) возврат компонентов (base, lang, topic, recency) и сохранять их в `users` (миграция: 4 колонки или JSON). В API `/users` и `/users/{login}` добавить эти поля. В ProfileDrawer и в UsersPage выводить горизонтальный breakdown-bar (base + similarity с подписями), рядом с ScoreRing.
- **Значимость.** Высокая. Это фундамент доверия к скорингу и база для любых «почему эта персона»-сценариев.
- **Сложность внедрения.** 2/5 — миграция + правка скоринга (~30 строк) + UI-компонент.

### 2.2. Панель состояния ML-модели

- **Какую проблему решает.** Owner не знает, работает ли ML-прогноз фоллобэков, какая у модели точность и на скольких примерах она обучена. Без этого карточка «ML followback candidates» — чёрный ящик.
- **Как лучше реализовать.** Эндпоинт `/api/ml/status`, читающий `models/current.json` (version, val_accuracy, num_samples, trained_at, top_languages/top_topics). Карточка на Management или в Overview: версия, точность, объём выборки, дата обучения, топ-5 признаков.
- **Значимость.** Средняя-высокая: повышает доверие к ML-блокам и показывает здоровье пайплайна.
- **Сложность внедрения.** 1/5 — чисто отображение готовых метаданных.

### 2.3. Глобальная аналитика языков и топиков

- **Какую проблему решает.** Owner не видит, какой технологический стек доминирует в его сети и где он пересекается со своим профилем. Это мешает точечно расширять сеть в нужных нишах (например, «у меня мало связей в Go-комьюнити»).
- **Как лучше реализовать.** Новые агрегаты в `queries.py` (частоты языков по весам и количеству пользователей, топ-топики) + страница/блок Analytics: treemap или bar-chart по языкам, облако/бары по топикам, подсветка языков, пересекающихся с профилем owner.
- **Значимость.** Высокая для стратегии развития связей (выбор ниши), средняя для оперативной работы.
- **Сложность внедрения.** 2/5 — SQL-агрегаты (частично уже есть: `get_global_language_frequencies`) + 1–2 компонента.

### 2.4. Тепловая карта активности (как contributions на GitHub)

- **Какую проблему решает.** История работы бота (follow по дням) не читается из списка последних действий; нельзя увидеть ритм и пики активности и сопоставить их с событиями.
- **Как лучше реализовать.** Heatmap за 365 дней из таблицы `actions` (аналог GitHub contributions): цвет по количеству follow-действий в день. Переиспользовать существующий `activity_timeline`, расширив его на год.
- **Значимость.** Средняя — наглядность, «пульс» системы.
- **Сложность внедрения.** 2/5 — один компонент + расширение запроса.

### 2.5. Раскрыть скрытые поля профиля из `github_profile_json`

- **Какую проблему решает.** Данные (возраст аккаунта, hireable, location, email, blog, twitter, public_gists) уже кэшированы в JSON, но почти не используются. А это — готовые «социально-профессиональные» атрибуты: локация и hireable напрямую влияют на релевантность связи.
- **Как лучше реализовать.** В ProfileDrawer добавить секцию «Детали» (аккаунт создан N лет назад, локация, blog, email, hireable, gists). В UsersPage — фильтр/сортировку по локации и hireable (данные извлекаются из JSON при запросе).
- **Значимость.** Средняя: обогащает карточку кандидата без новых API-вызовов.
- **Сложность внедрения.** 1/5 — поля уже приходят в `user_profile`; нужен только UI.

## 3. Уровень 2 — стратегические улучшения (средняя сложность)

### 3.1. Страница «Компании и организации»

- **Какую проблему решает.** Социально-профессиональные связи строятся не только с людьми, но и с организациями. Сейчас связи по компаниям есть в данных (`companies`, `user_companies`), но агрегированного взгляда «какие компании представлены в моей сети и сколько у меня там контактов» нет.
- **Как лучше реализовать.** Новая страница Companies: карточки компаний (avatar, name, description, location, число связей из `user_companies`, followers/репозитории компании, twitter/blog), сортировка по числу связей, клик — переход к списку связанных пользователей (переиспользовать `/users` с фильтром по компании). Данные для связей и списка — один-два SQL-запроса.
- **Значимость.** Высокая — прямо соответствует цели «развивать профессиональные связи» (B2B-взгляд на сеть).
- **Сложность внедрения.** 3/5 — страница + агрегаты + связка с Users.

### 3.2. Воронка конверсии follow → followback → unfollow

- **Какую проблему решает.** Owner не знает, насколько эффективна стратегия: какой процент подписок превращается во взаимные, за какое время, сколько людей отписываются. Без этого нельзя улучшать качество отбора.
- **Как лучше реализовать.** Аналитический блок на Overview: воронка (followed → followback → unfollowed) с абсолютными числами и % конверсии, а также график конверсии по неделям (из `actions` + `status`). Раздельно — время от FOLLOW до FOLLOWBACK (медиана).
- **Значимость.** Высокая — ключевая метрика эффективности всей системы.
- **Сложность внедрения.** 3/5 — агрегаты + 2 визуализации.

### 3.3. Исторические срезы для всех пользователей (мини-рост в профиле)

- **Какую проблему решает.** Тренд followers у конкретной персоны — сильный сигнал «растущий разработчик» (стоит связаться раньше других). Сейчас срезы пишутся только для owner, хотя схема и `store_user_snapshot()` готовы для любого пользователя.
- **Как лучше реализовать.** Расширить `_snapshot_targets()` в `workers/snapshot_worker.py` на всех `users` (status != DELETED) — бэкенд уже поддерживает (это заложено в дизайн). В ProfileDrawer добавить мини-график followers (и following/public_repos) из `user_snapshots` за последние 30–90 дней. Это согласуется с планом owner хранить срезы по всем users.
- **Значимость.** Высокая: раннее обнаружение растущих разработчиков + аналитика динамики сети.
- **Сложность внедрения.** 2–3/5: бэкенд почти готов (расширить список целей), UI — переиспользовать `FollowersChart`.

### 3.4. Очередь рекомендаций «Кого подписать дальше»

- **Какую проблему решает.** Owner вынужден сам комбинировать сортировку по score и ML-прогнозу. Нет единого структурированного списка «лучшие кандидаты с объяснением, почему».
- **Как лучше реализовать.** Блок/вкладка Recommendations: пользователи со status=NEW, отфильтрованные по score ≥ порога, отсортированные по score × ML-вероятности; у каждого — чипы причин («совпадение языков 80%», «общий топик: ai», «свежие репо», «растущий аккаунт»), кнопка «подписаться» (вызывает существующий джоб follow или напрямую), исключение уже отписавшихся.
- **Значимость.** Высокая — превращает дашборд из «пассивного отчёта» в инструмент действий.
- **Сложность внедрения.** 2/5 — SQL-выборка + переиспользование существующих компонентов.

### 3.5. Аналитика источника обнаружения (discovery funnel)

- **Какую проблему решает.** Неясно, какой канал приносит лучших кандидатов: органические фолловеры owner или граф вложенных подписчиков. Это влияет на то, куда направлять ресурсы коллектора.
- **Как лучше реализовать.** Группировка по `discovered_from` (owner_followers vs остальные) с агрегатами: количество, средний score, % followback, % DELETED. Отдельная секция в Analytics или Overview.
- **Значимость.** Средняя-высокая: оптимизация самого процесса сбора.
- **Сложность внедрения.** 2/5 — GROUP BY по `discovered_from` + таблица/бары.

### 3.6. История дневного бюджета follow

- **Какую проблему решает.** Карточка «Today's follows» показывает только текущий день; нет понимания динамики использования лимита (90/день), прогноза и пиков.
- **Как лучше реализовать.** График «follows по дням за 30 дней» с линией лимита (данные уже есть в `actions`), плюс сводка за неделю/месяц. Вписать в блок Analytics или заменить подпись KPI-карточки.
- **Значимость.** Средняя: контроль темпа развития сети.
- **Сложность внедрения.** 2/5.

### 3.7. Мониторинг лимитов GitHub API

- **Какую проблему решает.** Бот молча упирается в rate limit и уходит в cooldown; owner узнаёт об этом только из логов джоба. Оперативно понять «а не упёрлись ли мы в лимит» невозможно.
- **Как лучше реализовать.** Собирать заголовки `X-RateLimit-Remaining/Reset` (клиент их уже знает) в таблицу `api_usage` (дата, remaining, used, ресурс) и показывать на Management: текущий остаток, время сброса, график расхода за день. Предупреждение на Overview при remaining < 10%.
- **Значимость.** Средняя: прозрачность и профилактика простоев.
- **Сложность внедрения.** 3/5 — запись лимитов в клиенте + страница.

## 4. Уровень 3 — продвинутые возможности (высокая сложность, большой эффект)

### 4.1. Визуальный граф связей (network graph)

- **Какую проблему решает.** Трудно увидеть структуру сети: кто связан с кем через `discovered_from`, какие кластеры по языкам/компаниям образуются. Для «социально-профессионального» развития это самый наглядный инструмент.
- **Как лучше реализовать.** Force-directed граф (например, `react-force-graph` / d3): узлы — пользователи (цвет = основной язык или компания, размер = score), рёбра — `discovered_from`; фильтры по статусу/языку; клик — открытие ProfileDrawer. Ограничить граф топ-N (например, 300–500 узлов) для производительности.
- **Значимость.** Высокая (демонстрационно и стратегически), но вспомогательная к таблицам.
- **Сложность внедрения.** 5/5 — новая библиотека, виртуализация графа, бэкенд-эндпоинт с рёбрами.

### 4.2. Сравнение кандидата с профилем owner (radar / параллельные бары)

- **Какую проблему решает.** Один балл не объясняет сходство. Owner хочет за 5 секунд понять: «насколько этот человек похож на меня по стеку?».
- **Как лучше реализовать.** В ProfileDrawer — радиальная диаграмма: язык, топики, свежесть, активность (базовые метрики), где линия owner против линии кандидата. Переиспользовать уже считаемые в `services/scorer` данные (lang/topic/recency) — они станут доступны после п. 2.1.
- **Значимость.** Высокая для быстрых решений «знакомиться/подписываться».
- **Сложность внедрения.** 3/5 — зависит от п. 2.1 (компоненты скоринга).

### 4.3. Живой прогресс джобов (прогресс-бары + ETA)

- **Какую проблему решает.** Долгие джобы (score на десятки тысяч пользователей, silent) выглядят «зависшими»: статус RUNNING без информации о том, сколько уже обработано.
- **Как лучше реализовать.** Прогресс в БД: воркеры периодически пишут processed/total (например, в `job_runs` через JSON-поле или отдельную таблицу `job_progress`); `/api/jobs/{id}` возвращает прогресс; в Management — прогресс-бар и ETA. Требует точечных правок в `services/collector` / `services/scorer` (уже печатают `[idx/total]` — данные фактически есть на уровне логов).
- **Значимость.** Средняя-высокая: снижает тревожность и позволяет оценивать время.
- **Сложность внедрения.** 4/5 — сквозные изменения в воркерах и API.

### 4.4. Уведомления о значимых событиях

- **Какую проблему решает.** Owner узнаёт о новых взаимных подписках, падениях джобов и исчерпании лимитов только заходя на дашборд. Оперативность теряется.
- **Как лучше реализовать.** Слой событий (таблица `events` или проверка diff при polling) + каналы: встроенный центр уведомлений в UI, опционально Telegram/email (новая внешняя интеграция). События: новый followback, джоб упал, лимит исчерпан, новая партия кандидатов готова.
- **Значимость.** Высокая для «оперативного» развития связей — ключевое слово задачи.
- **Сложность внедрения.** 3–4/5 — механизм событий + интеграция каналов.

### 4.5. Экспорт данных (CSV / отчёт)

- **Какую проблему решает.** Аналитику вне дашборда (Excel, внешние сервисы) вести нельзя; данные «заперты» в SQLite.
- **Как лучше реализовать.** Эндпоинты `/api/export/users.csv`, `/api/export/snapshots.csv` и кнопки на страницах. Генерация на лету из существующих запросов (без новых библиотек).
- **Значимость.** Средняя.
- **Сложность внедрения.** 2/5.

## 6. Выводы

1. **Фундаментальный разрыв** — в UI не отображается *состав* скоринга и *состояние ML*, при этом именно эти два блока определяют, кому писать и с кем выстраивать связи. Их закрытие (2.1, 2.2) — минимальные трудозатраты при максимальном росте доверия к системе.
2. **Стратегический потенциал** уже заложен в данных: инфраструктура срезов (3.3), компании (3.1) и воронка (3.2) превращают дашборд из «отчёта о работе бота» в «карту профессиональной сети».
3. **Оперативность** достигается уведомлениями (4.4) и очередью рекомендаций (3.4) — именно эти два пункта отвечают на слово «оперативно» из задачи.
4. **Бюджет усилий**: пункты 2.1–3.4 (суммарно ~6–8 рабочих задач, 2–3/5 сложности каждая) дают наибольший прирост полезности и полностью покрывают цель документа. Тяжёлые визуализации (граф, radar) — вишенка на торте, их стоит делать после базовых блоков.
