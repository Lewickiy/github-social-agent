# API_using.md — Анализ нагрузки на GitHub API в silent mode

> Аналитический документ. Цель — посчитать, сколько запросов к GitHub API в час отправляет вся система при работе в **silent mode**, разложить нагрузку по эндпоинтам, выявить проблемные места и предложить варианты ускорения обработки **без выхода за пределы лимитов GitHub**.
>
> Документ основан на:
> - разборе кода (`services/silent.py`, `services/collector.py`, `core/github_client.py`, `core/config.py`, фоновые воркеры),
> - **реальных данных из рабочей БД** (`data/github_social.db`): распределение репозиториев по 887 собранным пользователям, доля форков, размер очереди silent,
> - **официальной документации GitHub** о лимитах REST API (primary 5 000 req/ч, secondary 900 pts/мин на эндпоинт).
>
> Код в рамках задачи не менялся.

---

## 1. Резюме (ключевые цифры)

| Показатель | Значение |
|---|---|
| **Основной лимит GitHub (PAT)** | **5 000 req/час** |
| **Текущая нагрузка системы (silent)** | **~600–800 req/час** (≈ 12–16 % лимита) |
| Самый нагруженный эндпоинт | `GET /repos/{owner}/{repo}/languages` — **~92 %** всех запросов |
| Вторичный лимит (per-endpoint) | 900 pts/мин — не достигается даже при 4 700 req/ч |
| Очередь silent (ждут обработки) | 33 421 пользователь |
| Время на очередь при текущих задержках | **~85–130 дней** |
| Резерв по основному лимиту | **6–8×** (можно ускорить в разы без риска) |

**Главный вывод:** система сейчас использует лишь ~12–16 % основного лимита GitHub. Узкое место — **не лимиты API, а искусственные задержки stealth-режима** (суммарно ~5 с сна на каждый репозиторий). Поэтому есть большой запас для ускорения в рамках лимитов: простая правка задержек даёт ~2×, а комбинация с пропуском языков форков и ограничением числа репозиториев — 3–6× по времени обработки.

## 2. Лимиты GitHub API (факты из документации)

### Основной (primary) лимит
- Аутентифицированные запросы (personal access token): **5 000 req/час** на токен.
- Неаутентифицированные: 60 req/час (проект всегда аутентифицирован — `GITHUB_TOKEN`).

### Вторичный (secondary) лимит — «зоны риска»
- **Не более 900 «поинтов» в минуту на один REST-эндпоинт** (обычный GET = 1 поинт, PUT/POST = 5 поинтов).
- Не более 100 одновременных запросов.
- Не более 80 «создающих контент» запросов/мин и 500/час (сюда относятся **подписки** — `PUT /user/following/{user}`).
- При превышении GitHub отвечает 403/429 с заголовком `Retry-After`; многократное превышение может привести к бану интеграции.

> **Следствие для проекта:** `GET /languages` = 1 поинт. Даже при 4 700 req/ч это ~78 pts/мин — **в 11 раз ниже** вторичного лимита 900 pts/мин. Реальная «красная зона» — только подписки (лимит 500/час, у нас 50/день — с огромным запасом).

## 3. Как устроен поток запросов в silent mode

Обработка одного пользователя в `SilentRunner.run()` (по коду `services/silent.py`):

| Шаг | Эндпоинт | Запросов | Комментарий |
|---|---|---|---|
| 1. Проверка существования | `GET /users/{user}` | 1 | + сохранение полного профиля в кэш |
| 2. Список репозиториев | `GET /users/{user}/repos` | 1–6 | `per_page=100`; >100 репо → пагинация (p90=115, p99=590) |
| 3. Языки каждого репо | `GET /repos/{owner}/{repo}/languages` | **N репо** | пропуск: свежие (<5 дней), пустые, >500 МБ, форки >50 МБ |
| 4. Скоринг | — | **0** | данные берутся из кэша (`github_profile_json`) — **бесплатно** |
| 5. Подписка (если score ≥ 35) | `GET /user/following/{user}` + `PUT /user/following/{user}` | 2 | до 50/день (`DAILY_FOLLOW_LIMIT`) |
| 6. Скан фолловеров owner | `GET /users/{owner}/followers` | 1 | каждые `OWNER_FOLLOWER_SCAN_INTERVAL=20` пользователей |

### Задержки (из `core/config.py`) — главный «тормоз»

| Параметр | Значение | Где применяется |
|---|---|---|
| `SILENT_DELAY_BETWEEN_REQUESTS` | **3 с** | после каждого `/languages` |
| `SILENT_DELAY_BETWEEN_REPOS` | **2 с** | после каждого репозитория |
| `SILENT_DELAY_BETWEEN_USERS` | 1 с | между пользователями |
| `SILENT_DELAY_BETWEEN_FOLLOWS` | 2 с | между подписками |
| `SILENT_DELAY_BETWEEN_SCORES` | 1 с | **не используется в run-цикле** (мёртвый параметр — см. п. 6.3) |

**Ключевая формула:** типичный пользователь (медиана 28 репо) тратит ~28×(3+2) = **~140 с только на сны**, при этом совершает ~30 запросов. При принятой в отчёте латентности 0,3 с/запрос сны съедают **~93 %** времени обработки пользователя (140 с из ~150 с).

### Фоновые воркеры (работают параллельно с silent)

| Воркер | Периодичность | Запросов за цикл | Эндпоинты |
|---|---|---|---|
| `FollowbackCheckWorker` | 1 раз/час | 33 юзера × 2 = **66** | `GET /users/{user}/following/{owner}`, `GET /user/following/{user}` |
| `CompanyWorker` | каждые 5 мин | 1 = **12/час** | `GET /users/{company}` |
| `SnapshotWorker` | 1–2 раза/день | 1–2 | `GET /users/{owner}` |
| `MLTrainerWorker` | 24 ч | **0** | только БД |

Суммарно воркеры добавляют **~70–80 req/час** короткими всплесками.

## 4. Текущая нагрузка по эндпоинтам (в час)

Расчёт на **реальной симуляции**: распределение репозиториев 887 собранных пользователей (медиана 28, среднее 62,5, p90=115, p99=590), задержки 1/2/3 с, сеть ~0,3 с на запрос.

| Эндпоинт | Запросов/час | Доля |
|---|---|---|
| `GET /repos/{owner}/{repo}/languages` | **460–680** | **~92 %** |
| `GET /users/{user}/repos` (с пагинацией) | 14–21 | ~3–4 % |
| `GET /users/{user}` | 11–16 | ~3 % |
| `GET /users/{owner}/followers` (раз в 20 юзеров) | ~1 | <1 % |
| `GET/PUT /user/following/{user}` (подписки) | ~0–4 | <1 % |
| **Итого: основной silent-цикл** | **~500–700** | 100 % |
| Воркеры (followback + company) | +70–80 | всплески |
| **ВСЕГО система** | **~600–800 req/час** | ≈ 12–16 % лимита 5 000 |

> Разброс 460–680 у `/languages` объясняется долей форков, попадающих под фильтр: фильтр пропускает только форки **>50 МБ** (а размер репо в БД не хранится), поэтому фактически языки запрашиваются почти у всех репо, включая мелкие форки. Реалистичная оценка — **~650 req/ч** на основной цикл.

## 5. Очередь и прогноз времени обработки

В БД сейчас **33 421 пользователь** ожидает сбора репозиториев и скоринга (по логике `users_for_silent_processing`).

| Сценарий задержек | req/час | % лимита | Время на очередь 33 421 |
|---|---|---|---|
| **Текущий (1/2/3 с)** | ~650 | 13 % | **~85–130 дней** |
| Быстрый (1/1/1 с) | ~1 100 | 22 % | ~39 дней |
| Оптимальный (7.1+7.2+7.4, см. п. 8) | ~900–1 200 | 18–24 % | **~15–25 дней** |
| Агрессивный (0/0/0,5 с) | ~4 700 | 94 % | ~9 дней ⚠️ у предела |

**Проблема №1 отчёта:** при текущих настройках полный прогон очереди займёт **3–4 месяца**. При этом лимиты использованы всего на ~13 % — это явный дисбаланс «тратим месяцы, но не используем выделенный бюджет API».

## 6. Проблемные места

### 6.1. `/languages` — 92 % всех запросов, и это самый «спящий» эндпоинт
- **Проблема.** На каждый репозиторий уходит 3 с сна после `/languages` + 2 с сна после репо. При медиане 28 репо — ~140 с на пользователя. При этом языки форков (а их **54 %** всех собранных репо) почти всегда повторяют языки исходного репозитория — польза для скоринга минимальна, а запросы и сны тратятся полностью.
- **Факт из БД:** 30 007 из 55 422 репо — форки (54 %).

### 6.2. Скоринг «бесплатный», но данные для него собираются тяжело
- **Проблема.** Скоринг сам по себе не делает запросов (кэш профилей) — это хорошо. Но чтобы получить языки/топики для скоринга, приходится сначала собрать **все** репозитории пользователя, включая сотни у «тяжёлых» пользователей (p99 = 590 репо → 6 страниц пагинации + до 590 вызовов `/languages`).

### 6.3. Мёртвый параметр конфигурации
- `SILENT_DELAY_BETWEEN_SCORES = 1` импортируется в `services/silent.py`, но **не используется** в цикле обработки (скоринг идёт сразу после сбора, без отдельного сна). Параметр вводит в заблуждение.

### 6.4. Нет условных запросов (ETag / If-None-Match)
- **Проблема.** GitHub поддерживает условные запросы: при отправке `If-None-Match` с ранее полученным `ETag` ответ `304 Not Modified` **не засчитывается в лимит**. Клиент (`core/github_client.py`) не хранит ETag и не использует условные запросы — повторные сборы репозиториев (раз в 7 дней) оплачиваются полностью.

### 6.5. Размер репозитория не сохраняется в БД
- **Проблема.** Фильтр «не запрашивать языки у форков >50 МБ и репо >500 МБ» (`should_fetch_languages`) оценивается на лету по ответу API, но **размер не сохраняется** в таблицу `repositories`. На повторных прогонах нельзя отсеять тяжёлые репо без запроса — фильтр работает вслепую.

## 7. Предложения по ускорению (в рамках лимитов)

> Каждое предложение — блок: **проблема → реализация → эффект → значимость → сложность** (1–5). Код не менялся — это план.

### 7.1. Уменьшить задержки `SILENT_DELAY_BETWEEN_REQUESTS` и `SILENT_DELAY_BETWEEN_REPOS` до 1 с
- **Проблему решает.** ~93 % времени обработки уходит на сны; основной лимит использован на 13 %.
- **Реализация.** В `core/config.py`: `SILENT_DELAY_BETWEEN_REQUESTS = 1`, `SILENT_DELAY_BETWEEN_REPOS = 1`. Jitter (±30 %) уже встроен в `_jitter()`.
- **Эффект.** ~650 → ~1 100 req/ч (22 % лимита); очередь 39 дней вместо 85–130.
- **Значимость.** Высокая — самый простой и безопасный выигрыш.
- **Сложность.** 1/5 — правка двух констант.

### 7.2. Не запрашивать языки у форков вовсе (а не только у «больших»)
- **Проблему решает.** 54 % репо — форки; их языки дублируют исходники и почти не влияют на скор схожести.
- **Реализация.** В `should_fetch_languages` (`core/github_client.py`) (или в месте вызова в `services/silent.py`/`services/collector.py`) добавить: `if repo.get("fork"): return False`. Топики всё равно берутся бесплатно из ответа `/repos`.
- **Эффект.** Число вызовов `/languages` падает примерно вдвое → суммарно ~40–50 % меньше запросов и времени.
- **Значимость.** Высокая — двойной эффект (меньше запросов И меньше снов).
- **Сложность.** 1/5 — пара строк; **риск:** скоринг схожести по языкам станет чуть грубее для пользователей, у которых почти все репо — форки (редкий кейс, т.к. топики и recency остаются).

### 7.3. Условные запросы (ETag / `If-None-Match`) для `/repos` и `/languages`
- **Проблему решает.** Повторные сборы (раз в 7 дней) оплачиваются по полной; лимит при этом почти не используется.
- **Реализация.** В `core/github_client.request()` принимать `etag` из заголовков ответа, сохранять его (например, в `repositories.last_checked_at` рядом или в отдельную колонку) и отправлять `If-None-Match` при повторном запросе. Ответ 304 → данные не изменились, **запрос не списывается с лимита**.
- **Эффект.** Повторные прогоны очереди становятся почти бесплатными по лимиту; скорость ограничена только временем ответа 304.
- **Значимость.** Средне-высокая — лучший долгосрочный инструмент против «мёртвого» расхода лимита.
- **Сложность.** 3/5 — правки клиента, хранение ETag, обработка 304.

### 7.4. Ограничить число репозиториев на пользователя (топ-N по свежести)
- **Проблему решает.** «Тяжёлые» пользователи (p99 = 590 репо) съедают непропорционально много запросов и времени: 6 страниц пагинации + до 590 вызовов `/languages`. Для скоринга (гистограмма языков, топики, свежесть) достаточно самых свежих репо.
- **Реализация.** В `core/github_client.repos()` ограничить пагинацию первыми 2–3 страницами (200–300 репо) или собирать только репо, обновлённые за последние N лет (параметр `sort=updated` уже стоит). Для ~90 % пользователей это ничего не меняет (p90 = 115 репо), а хвост распределения обрезается.
- **Эффект.** Пагинация почти исчезает; число `/languages` у хвоста распределения падает в разы.
- **Значимость.** Средне-высокая — сглаживает «толстый хвост» очереди.
- **Сложность.** 2/5 — ограничение в клиенте + константа.

### 7.5. Сохранять размер репозитория в БД (для фильтра языков на повторных прогонах)
- **Проблему решает.** Фильтр `should_fetch_languages` (форки >50 МБ, репо >500 МБ) сейчас работает вслепую, т.к. размер не хранится.
- **Реализация.** Добавить колонку `size_kb` в `repositories` (миграция), заполнять при `save_repository`. На повторных прогонах отсекать тяжёлые репо **без** дополнительного знания (данные уже в БД).
- **Эффект.** Устраняет «слепые» запросы языков к заведомо тяжёлым репо; заодно делает прогон 7.2 точнее (пропускать только тяжёлые форки).
- **Значимость.** Средняя — вспомогательная оптимизация.
- **Сложность.** 2/5 — миграция + правка `save_repository`.

### 7.6. Убрать мёртвый `SILENT_DELAY_BETWEEN_SCORES`
- **Проблему решает.** Вводит в заблуждение: кажется, что есть пауза между скорингами, а её нет.
- **Реализация.** Удалить из импорта в `services/silent.py` (или начать использовать — лишний 1 с сна между скорингами не нужен, т.к. скоринг не делает запросов).
- **Эффект.** Гигиена конфигурации.
- **Значимость.** Низкая.
- **Сложность.** 1/5.

### 7.7. (Опционально) Второй токен / ротация токенов
- **Проблему решает.** Лимит 5 000 req/ч — на токен. Если упереться в 5 000 (потребуется только при агрессивных настройках), ротация двух токенов удваивает бюджет.
- **Реализация.** Список токенов в конфиге, round-robin в `get_headers()`. Актуально только для сценария >4 000 req/ч.
- **Эффект.** Потолок 10 000 req/ч.
- **Значимость.** Низкая сейчас (мы на 13 %), высокая как страховка.
- **Сложность.** 2/5.

## 8. Сводная таблица сценариев ускорения

| Комбинация | req/час | % лимита 5 000 | Очередь 33 421 | Риск вторичного лимита |
|---|---|---|---|---|
| **Текущая (1/2/3)** | ~650 | 13 % | 85–130 дней | нет |
| 7.1 (1/1/1) | ~1 100 | 22 % | ~39 дней | нет |
| 7.1 + 7.2 (1/1/1 + без языков форков) | ~1 000–1 100 | 20–22 % | **~20–25 дней** | нет |
| 7.1 + 7.2 + 7.3 (+ETag) | ~1 000–1 100 (raw) | 20–22 % от лимита; фактически списывается ~10–15 % (304 бесплатны) | ~20 дней, повторные прогоны почти бесплатны | нет |
| 7.1 + 7.2 + 7.4 (+топ-N репо) | ~900–1 200 | 18–24 % | **~15–25 дней** | нет |
| Агрессивный максимум (0/0/0,5 + всё выше) | ~4 700 | 94 % | ~9 дней | ⚠️ вплотную к primary; вторичный не достигается (78 pts/мин < 900) |

**Рекомендуемая комбинация:** 7.1 + 7.2 + 7.4 (+ 7.3 в перспективе). Это даёт **3–6× ускорение по времени обработки** (85–130 дней → ~15–25 дней) при 18–24 % использования лимита — максимальный эффект при минимальном риске.

> **Почему не «агрессивный» сценарий:** 4 700 req/ч оставляет лишь 6 % запаса до бана по primary-лимиту; при любом внешнем запросе (например, ручной команде из дашборда) можно вылететь в 403. Запас в 2–4× (как в рекомендованной комбинации) — золотая середина: быстрее в разы, но с безопасной подушкой.

## 9. Ограничения анализа

1. **Размер репо не хранится в БД**, поэтому доля репо, реально попадающих под фильтр «тяжёлых» (пустые, >500 МБ, форки >50 МБ), оценена по косвенным данным (доля форков 54 %). Диапазон 460–680 req/ч по `/languages` покрывает обе крайности.
2. Симуляция использует распределение репозиториев **уже собранных** 887 пользователей как прокси для необработанной очереди — это лучшая доступная оценка.
3. Реальная скорость зависит от латентности сети до api.github.com (принято 0,3 с на запрос; при 0,1 с скорость выше, при 0,5 с — ниже).
4. Лимиты GitHub «subject to change» (вторичные — без предупреждения); документ опирается на актуальную официальную документацию (проверено при подготовке отчёта).

## 10. Выводы

1. **Система недоиспользует выделенный бюджет API в 6–8 раз.** Текущие ~600–800 req/ч — это 12–16 % от лимита 5 000 req/ч. Узкое место — не лимиты, а stealth-задержки (~93 % времени обработки уходит на сны).
2. **92 % запросов — `/languages`.** Именно этот эндпоинт определяет и число запросов, и время обработки. Любая экономия на нём (пропуск форков, ETag, топ-N репо) даёт максимальный эффект.
3. **Быстрый выигрыш без риска:** снизить задержки до 1/1/1 (п. 7.1) → ~1 100 req/ч, очередь ~39 дней. Комбинация 7.1+7.2+7.4 → **~15–25 дней (3–6× ускорение по времени)** при 18–24 % лимита.
4. **Подписки — единственная «красная зона»**, но она далека: 50/день против вторичного лимита 500/час (и primary-лимит на PUT не применяется отдельно — списываются поинты).
5. **Перспектива:** внедрение условных запросов (ETag) сделает повторные прогоны очереди почти бесплатными по лимиту и позволит со временем перейти на более частые обновления данных (например, репозитории раз в 3–4 дня вместо 7) без роста расхода лимита.
